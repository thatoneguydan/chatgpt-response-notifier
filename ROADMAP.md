Preserve **3 silent-stop reloads**, **5 explicit-interruption reloads**, **5-minute surviving explicit retry spacing**, **1 recovery Continue per incident**, and **12 generation-producing actions per trusted human-started run** only as inner incident/run ceilings. ### Scope and required behavior

- Use the stable Firefox for Android browser with a small companion extension; Chrome remains the desktop browser on Glass. Cover both new conversations and another human message in an existing conversation. The ChatGPT Android app is out of scope. Mozilla documents [Android extension development](https://extensionworkshop.com/documentation/develop/developing-extensions-for-firefox-for-android/) and [signed/self-distributed add-ons](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/); verify the actual installation/update route on stable Android before committing to distribution.
- **Chrome-open and Chrome-closed operation are equally required.** An extension cannot receive events with Chrome fully exited. Prefer the existing Windows helper as the independent receiver and lifecycle owner: its [application lifetime](src/ChatGPTResponseNotifier.Host/NativeHostApplication.cs) is independent of browser clients, and [per-user startup registration](src/ChatGPTResponseNotifier.Core/StartupRegistration.cs) already exists. Those are source capabilities, not evidence that a mobile receiver or browser launcher already exists; re-inspect current source and live helper health at implementation time.
- A confirmed mobile send should produce a durable handoff containing the conversation identity, paired destination, unique event ID, sequence/freshness metadata and sufficient turn-binding evidence. Do not forward prompt/response bodies, ChatGPT credentials or session tokens. For a new chat, wait for its real persisted conversation identity; typing, navigation, an optimistic Send click or an old footer is not proof of a new accepted turn. Ordinary signed-in conversation URLs must not be replaced with public shared-conversation links.
- The receiver must work over home Wi-Fi and away from home. Prefer an authenticated durable relay/mailbox with an outbound connection from the helper; choose the smallest maintainable transport after the feasibility gate. Preserve the existing extension-origin validation and loopback-only WebSocket. Do not expose that local bridge on the LAN/Internet or accept arbitrary remote commands, executable paths or launch arguments.
- With Chrome connected, reuse the exact matching conversation tab and update it only when fresh turn evidence requires it. With Chrome fully closed, persist the event, launch the explicitly paired Chrome installation/profile through a supported per-user route, await the expected extension handshake, and then reconcile restored tabs before opening another. An absent bridge alone is not proof that Chrome is closed: disabled extensions, a hung runtime and wrong profiles must not cause repeated launches or duplicate windows.
- The helper/relay keeps pending work until the desktop extension acknowledges the correct conversation and turn are actually enrolled. Distinguish relay acceptance, helper persistence, browser connection and monitoring-active acknowledgements. A browser process start or a successful socket write is not monitoring success.
- No direct ChatGPT backend/session API calls, conversation polling, sidebar-refresh discovery or periodic page reloads. Companion/relay messaging uses our own transport. Any necessary ChatGPT page open/reload is tied to fresh accepted activity, deduplicated and admitted through the existing profile traffic governor/breaker; protect desktop drafts/uploads and current generation. Preserve explicit Pause/manual Stop, eligibility/status rules, per-run budgets and uncertainty stops. The mobile companion observes/hands off; Glass remains the sole automation owner.
- Glass must be powered on/awake with the intended user session and receiver available for immediate handling. If Glass sleeps, is offline, restarts or has no usable signed-in session, retain pending delivery and reconcile on resume/login. Define expiry and revalidate the latest turn before any later automation; never replay stale automatic Sends or create wake/relaunch loops. Automatic PC power-on/wake and Windows login bypass are outside this feature.
- Keep reception and relay reconnection windowless. Chrome startup is the user-requested application launch; use the narrowest supported launch behavior, avoid extra focus/virtual-desktop manipulation, and verify its actual presentation. Do not promise an invisible cold start. Preserve stable extension identity, helper ownership, rollback and the normal protected deployment route.
